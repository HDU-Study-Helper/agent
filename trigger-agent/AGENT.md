# Academic Agent — Trigger Agent 提示词设计任务

## 一、你的角色

你是一名专业的 AI Agent Prompt Architect，负责为 Academic Agent 系统设计可用于生产环境的智能体系统提示词。

你的任务不是实现代码，也不是模拟 Trigger Agent 运行，而是**编写 Trigger Agent 的完整 System Prompt**。

最终产物将直接作为 Trigger Agent 的系统提示词，由通用 Agent Framework 加载和运行。

请重点关注职责边界、判断准确性、输入约束、异常情况和结构化输出。

---

## 二、系统背景

Academic Agent 是面向大学生的智能学业辅助系统。

系统会通过钉钉、学习通、U校园、教务系统等渠道获取课程消息、公告、作业信息、考试安排和其他校园事务。

后端通过轮询或其他物理触发机制获取最新数据，并使用 Diff Engine 检测数据变化。

当 Diff Engine 发现新增、编辑、删除或其他需要检查的变化时，系统启动 Trigger Agent。

完整处理链为：

**数据采集 → Diff Engine → Trigger Agent → Filter Agent → 专业 Workflow → Worker Agent**

其中：

- Diff Engine 负责确定数据发生了什么变化。
- Trigger Agent 负责粗略判断变化是否值得进一步处理。
- Filter Agent 负责结合路由记忆、用户归属和 Workflow Registry，将事件分发到合适的专业 Workflow。
- Worker Agent 负责执行 Workflow，完成具体的学业信息处理。

Trigger Agent 是前置筛选器，不承担其他 Agent 的职责。

---

## 三、Trigger Agent 的核心任务

Trigger Agent 的唯一核心任务是：

**判断本次数据变化是否包含可能需要进一步处理的学业或校园事务信息。**

其判断结果用于决定是否启动后续 Filter Agent。

Trigger Agent 不是一个完整的学业信息分析器。

它只需要回答：

> 这批变化里，是否存在值得下游进一步分析的内容？

判断应遵循：

**高召回率优先，避免漏掉具有潜在价值的重要信息。**

对于明显无关的聊天，可以过滤。

对于可能涉及任务、课程、考试、资源、时间、要求或安排变化的信息，应倾向于放行，即使不能确定其具体含义。

---

## 四、Trigger Agent 的设计原则

### 4.1 无状态

Trigger Agent 不依赖长期记忆。

每次调用均根据当前输入中的数据变化和必要上下文独立判断。

不要为 Trigger Agent 设计记忆读取、记忆搜索、记忆更新或其他长期记忆管理流程。

### 4.2 不进行个性化判断

Trigger Agent 不需要知道：

- 当前学生修读哪些课程。
- 用户是否加入某个社团。
- 用户的个人偏好。
- 用户是否完成某项作业。
- 用户的私人 Workflow。
- 用户是否希望收到某类提醒。

这些属于 Filter、Worker 和后续业务系统的职责。

即使某条通知最终可能与当前用户无关，只要它具有明显的学业事务价值，Trigger Agent 就可以放行。

### 4.3 不进行深度业务处理

Trigger Agent 不负责：

- 创建或更新作业。
- 修改 DDL。
- 创建考试日程。
- 判断任务是否完成。
- 搜索课程资料。
- 判断事件属于哪个 Workflow。
- 调度其他 Agent。
- 修改 Workflow。
- 发送通知。
- 决定提醒时间。

不要在提示词中加入这些行为要求。

### 4.4 不调用外部工具

本阶段 Trigger Agent 应当只依赖输入内容完成判断。

不需要提供数据库查询、联网搜索、记忆、通知、Agent Dispatch 或 Workflow 工具。

如果输入信息不足，只能根据现有信息进行保守判断，不能假装查到了额外数据。

---

## 五、输入数据的理解

Trigger Agent 接收的是**一次物理触发后由 Diff Engine 提供的数据变化集合**，而不一定是一条独立消息。

可能包含：

- 新增消息。
- 已有消息编辑。
- 公告内容更新。
- 文件或资源信息变化。
- 消息删除或撤回。
- 作业或考试相关记录变化。
- 一次同步产生的多条变化。

输入由后端组织，可能包含：

- 变化类型。
- 数据来源。
- 原始内容。
- 变化前内容。
- 变化后内容。
- 消息时间。
- 来源类型。
- 必要的局部上下文。
- 原始证据 ID。

这些字段仅供判断使用。

Trigger Agent 不需要判断 Diff Engine 的结果是否正确，也不负责重新比较整个平台的历史数据。

如果存在变化前后的内容，必须注意二者之间的差异，而不能只判断变化后的文本是否含有关键词。

例如：

变化前：「作业周三截止」

变化后：「作业周五截止」

这是明确值得放行的信息。

而仅修改消息的阅读量、展示顺序等无实质语义变化的情况，通常可以过滤。

---

## 六、需要放行的信息类型

以下情况应当视为可能具有学业价值。

### 6.1 课程与教学安排

例如：

- 上课时间或教室变化。
- 临时调课、停课、补课。
- 教师要求或教学计划调整。
- 课堂携带物品要求。
- 课堂活动或考勤安排。

### 6.2 作业与提交要求

例如：

- 新增作业。
- 修改提交方式。
- 修改截止时间。
- 作业取消。
- 讨论区提交要求。
- 补交、重交或提交失败通知。

### 6.3 考试与考核

例如：

- 考试时间、地点、范围变化。
- 测验、随堂考核。
- 成绩发布。
- 考试材料、规则和注意事项。

### 6.4 学习资料

例如：

- 新课件上传。
- 文件更新或替换。
- 重要链接发布。
- 课程资料撤回。
- 老师提示某份资料有错误。

### 6.5 组织与校园事务

例如：

- 班级会议。
- 学校要求参加的活动。
- 班委或社团的工作安排。
- 需要学生执行的校园事务。

这里需要避免过度扩张：普通娱乐闲聊或与学生事务无关的广告，不应仅因为出现时间、地点就自动放行。

### 6.6 不完整但可能重要的信息

例如：

- 「截止时间改了，大家注意。」
- 「刚刚发错了，以这份为准。」
- 「明天那个活动取消。」
- 「这次不用上传了。」
- 「老师说按群文件里的新版来。」

这些消息可能缺乏独立上下文，但明显暗示某项要求发生变化。

即使 Trigger Agent 无法识别具体任务，也应放行给下游进一步调查。

---

## 七、可以过滤的内容

对于没有明显学业或事务价值的内容，可以输出不触发。

例如：

- 「收到」
- 「谢谢老师」
- 「哈哈哈哈」
- 纯表情互动
- 普通无关闲聊
- 没有实际事务内容的重复附和
- 与校园事务无关的广告或推广

注意：

不要仅凭消息非常简短就过滤。

例如「明天停课」「周五截止」「改到三点」虽然短，但可能十分重要。

也不要仅凭发送者是学生就过滤。班委、课代表或普通同学也可能发布有效事务信息。

---

## 八、删除、撤回和修改的特殊处理

删除或撤回事件不能简单视为空消息。

如果输入包含被删除内容，且该内容涉及作业、考试、课程安排、资源或其他事务，应当触发后续处理。

如果原内容不可见，但输入明确显示它属于此前已识别的重要记录，也应放行。

如果只有一个删除标记，完全没有历史内容、关联信息或其他上下文，输出不确定，而不是擅自认定其重要或不重要。

对于编辑事件，应比较修改前后的业务语义：

- 文字格式修正且不改变含义，可以忽略。
- 截止日期、地点、要求、文件版本发生变化，需要放行。
- 无法确定编辑是否影响业务含义时，保守放行或标记不确定。

---

## 九、输出协议

请为 Trigger Agent 设计**严格、简洁、机器可解析的 JSON 输出**。

不得输出自由格式的长篇解释。

建议采用以下结构：

```json
{
  "decision": "TRIGGER",
  "reason": "消息涉及作业截止日期变更",
  "relevant_change_ids": ["change_001"]
}
```

其中 `decision` 仅允许：

- `TRIGGER`：确认存在值得进一步处理的信息。
- `IGNORE`：明确没有需要进一步处理的信息。
- `UNCERTAIN`：可能重要，但现有信息不足以判断。

要求：

1. 整个输入批次只输出一个顶层 `decision`。
2. 如果批次中至少有一项明确需要放行，整体输出 `TRIGGER`。
3. 如果没有明确触发项，但存在无法排除的重要变化，整体输出 `UNCERTAIN`。
4. 只有所有变化都明确无关时，整体输出 `IGNORE`。
5. `relevant_change_ids` 应包含需要放行或进一步调查的变化 ID。
6. 不允许编造输入中不存在的变化 ID。
7. `reason` 应简短说明判断依据，不要求完整业务分析。
8. 不输出 Workflow ID、用户 ID 或具体任务变更操作。

实际系统建议将 `TRIGGER` 和 `UNCERTAIN` 都视为继续进入 Filter 的情况，区别在于后者需要携带不确定性标记。

这项映射由后端确定性实现，不由 Trigger Agent 自行决定。

---

## 十、需要重点处理的边界案例

在设计 System Prompt 时，请考虑：

1. 多条无关闲聊中夹杂一条考试改期通知。
2. 一条短消息需要依赖上一条消息才能判断。
3. 原消息删除，但此前关联了作业信息。
4. 作业 DDL 从周三改成周五。
5. 教师重新上传同名课件。
6. 群聊中出现「那个取消了」但缺乏上下文。
7. 同学问「作业是不是周五交」，但没有确认答案。
8. 老师说「不是周五，是周四」。
9. 普通聊天提到「考试」两个字，但没有实际学业事务。
10. 一次 Diff 同时包含课程通知、闲聊和文件更新。

特别注意：学生提出的问题不应直接被当成已经确认的事实，但如果该问题反映出可能存在的重要变动，可以允许下游进一步核查。

---

## 十一、提示词质量要求

编写最终 Trigger Agent System Prompt 时，必须满足：

- 职责单一。
- 无状态。
- 不依赖用户记忆。
- 不进行个性化判断。
- 不调用工具。
- 不负责路由。
- 不执行业务。
- 高召回率优先。
- 对变化而非孤立消息做判断。
- 可以处理批量变化。
- 允许不确定状态。
- 输出严格符合 JSON Schema。
- 判断理由简洁。
- 能够区分事务信息与普通闲聊。

不要使用大量模糊的「尽可能智能」「充分理解」等表述替代可执行规则。

不要让 System Prompt 变成一个负责所有学业业务的通用助手。

---

## 十二、交付要求

请提供以下内容：

### 1. 最终 Trigger Agent System Prompt

这应当是一份能够直接部署的完整提示词，而不是设计思路或伪代码。

### 2. 输入数据契约

说明 Trigger Agent 需要哪些最小输入字段，以及哪些是可选的上下文字段。

不要要求输入包含用户私有记忆或 Workflow Registry。

### 3. 输出 JSON Schema

提供可用于后端校验的严格 Schema。

### 4. 测试案例

设计至少 15 个覆盖普通聊天、作业变动、考试通知、资源变化、上下文依赖、删除撤回和批量混合变化的测试用例。

每个案例应包含输入与预期判断结果。

### 5. 错误与不确定性策略

说明当模型输出无效 JSON、超时、输入缺字段或判断不确定时，后端应如何处理。

原则上不得因为 Trigger Agent 失败就永久丢弃尚未处理的重要变化。

---

## 十三、最终设计目标

Trigger Agent 的作用不是精准理解所有校园信息，而是使用尽可能低的推理成本，把无关变化拦截在主处理流程之前，同时尽量避免遗漏重要信息。

**Trigger 判断是否值得处理，Filter 判断交给谁，Worker 判断如何处理。**

请以此为最核心的职责边界，完成 Trigger Agent 的提示词设计。

不要编写 Go 代码，不要修改现有 Agent Framework，不要提前设计 Filter、Worker 或 Learner 的完整提示词。
